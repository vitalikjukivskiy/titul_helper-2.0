# Як випускати нову версію

У проєкті використовується одна постійна гілка `main`, один універсальний workflow `.github/workflows/release.yml` і GitHub Releases із тегами виду `vX.Y.Z-beta`.

## Звичайний реліз

1. Внести зміни в окремій робочій гілці.
2. Відкрити Pull Request у `main` і дочекатися зеленого `Validate build`.
3. Оновити `CHANGELOG.md`.
4. Оновити `RELEASE_NOTES.md` — цей текст буде показаний користувачам у GitHub Release та в механізмі автооновлення.
5. Змінити `VERSION`, наприклад з `2.0.13-beta` на `2.0.14-beta`.
6. Злити Pull Request у `main`.

Зміна `VERSION` автоматично запускає `.github/workflows/release.yml`. Workflow:

- перевіряє формат версії;
- перевіряє бази вікторин і захисну логіку TitulHelper;
- компілює Assistant і `CyberPW Updater.exe`;
- формує `CyberPW-Assistant-2.0-Beta-Portable.zip`;
- створює або оновлює тег `v<VERSION>`;
- публікує GitHub Release;
- перевіряє, що release asset існує.

## Hotfix

Hotfix робиться так само. Назву робочої гілки можна зробити `hotfix/<коротка-назва>`, але після merge джерелом істини лишається тільки `main`. Для hotfix обов'язково підняти patch-версію, наприклад `2.0.13-beta` → `2.0.14-beta`.

## Важливо

- Не створювати новий репозиторій під кожну версію.
- Не створювати окремий release-workflow під кожен номер версії.
- Не змінювати вже опублікований старий тег для нового коду.
- Один реліз = один унікальний тег.
- Історія змін зберігається в `CHANGELOG.md`, а короткий текст поточного релізу — в `RELEASE_NOTES.md`.
